# Второй пакет аудита BMS Zigbee

Версия дополнения **2.14.2-bms.8**, Z2M **2.14.2**, converters **26.115.1**, ядро **10.10.0-bms.3**.
Пакет построен поверх первого пакета (PR #1). Его отдельный PR имеет базой `codex/zigbee-first-package`, пока первый PR не слит в `main`.

## Проблема и результат

Возврат конвертера ещё не означал завершения всех его отправок: он мог запустить вложенный вызов без await или выйти из Promise.all по первой ошибке. Более новая команда участнику/группе могла пройти после преждевременного снятия барьера. Кроме того, coalescer получал resolved Promise сразу после постановки в очередь.

Патч `0006-command-inflight.patch` удерживает барьер до завершения всех уже начатых через обёртку ZCL-вызовов. Отдельная очередь операций сериализует их по IEEE, группа резервирует также IEEE участников. Несвязанные устройства работают параллельно. Отправка из coalescer возвращает настоящий handle завершения; приём MQTT остаётся неблокирующим. При отключённом ограничении частоты сохраняется порядок операций.

Ручные `bms_dp` и `configureMagicPacket` расширения Tuya используют общий runtime очереди. Одновременные announce/interview одного IEEE объединяются на время инициализации. Ошибка освобождает очередь; следующая попытка по новому событию разрешена. Внешний слой в обычном upstream Z2M без runtime сохраняет прямой вызов.

Патч `0007-extension-status.patch` публикует retained `bridge/bms/extensions`. Ошибка импорта, отсутствующий файл, `.invalid` или исключение `start()` дают `degraded`, успешный `start()` всех обязательных расширений — `ready`. Частично запущенное расширение с ошибкой очищается через штатное отключение. Контроллер также публикует `degraded`, если обязательный слой отключён настройкой external JS. Ошибки публикации диагностики логируются и не запрещают загрузку.

## Проверка

На чистом клоне тега Z2M 2.14.2 применены все семь сохранённых патчей. `addon/tools/check-z2m.sh` устанавливает закреплённое ядро, запускает Biome, сборку TypeScript, полный Z2M suite и Tuya suite. Только после успеха записывает `.work/z2m-tested.json` с хешами 121 файла dist (без upstream-маркера `.hash`). Изменение входных патчей, версии или SHA ядра делает этот результат устаревшим.

Локальные результаты:

- Z2M: **914/914**, 31 тестовый файл.
- Tuya: **60/60**.
- Защита сборки и согласованности stage: **10/10**.
- Отдельный прогон очереди и загрузчика: 40/40; новый `BmsOperationQueue` — 100% строк, ветвей и функций (это не покрытие всего проекта).
- Biome и TypeScript проходят. `verify-stage.cjs` подтверждает совпадение исходников, упакованного слоя, закреплённого ядра и паспорта.

Новые сценарии воспроизводят отделённый конвертером вызов, два одновременно начатых вызова группе, ожидающую DP/init-процедуру, восстановление очереди после ошибки, реальную ошибку start/import, missing/invalid/removal, отключение external JS, устаревший stage и подмену скомпилированного Z2M.

Повторение из корня репозитория:

```bash
bash core/build.sh
bash addon/tools/check-z2m.sh
bash addon/stage.sh
node addon/tools/verify-stage.cjs
node --test addon/test/*.test.cjs
```

При намеренном изменении ядра отдельно сверить новый архив и обновить `bms-core-sha256` в `versions.json`; автоматического принятия произвольного SHA нет. В CI дополнительно запускаются harness и полная проверка ядра, после stage проверяется отсутствие изменений файлов выпуска и собирается amd64 Docker-образ без публикации.

## Границы

Живая сеть, SLZB-06M и Home Assistant не использовались. Ни успешный API-вызов, ни MQTT state не считаются доказательством физического переключения. `ready` означает завершение start расширений, а не доступность HA или устройств. Проверка исполнения на негрупповом TS0002 и измерение нужной MCU-паузы остаются задачами пилота.

Очередь охватывает начатые вызовы Publish и подключённые BMS DP/init-процедуры. Она не перехватывает будущие таймеры сторонних скриптов, фоновые операции всех upstream-расширений и обязательные служебные ответы Tuya. Произвольные задержки по моделям, радио, CCA и прошивка в этом пакете не менялись.

Пилот после проверки и принятия PR: одна комната с 11 каналами, негрупповое реле и ползунок ламп; сценарии group→unicast, unicast→group, пересекающиеся группы, announce одновременно с командами. Отдельно учитывать приём намерения, попытку отправки, device report и физическое исполнение; критерии задержек и потерь согласовать до запуска.
