# tuya/layer — слой Tuya для Zigbee2MQTT

Файлы, которые дополнение «BMS Zigbee» кладёт в папку данных Z2M 2.14.2 (converters 26.115.1), чтобы
улучшать совместимость Tuya и добавлять описания новых моделей. Равенство с родным хабом требует отдельного сравнения на устройствах.

| Путь | Что |
|---|---|
| `external_extensions/bms-tuya-service.mjs` | Расширение: служебные ответы Tuya, «магический пакет», сырые точки `dp_<номер>` и команда `bms_dp` |
| `external_extensions/bms-area-groups.mjs` | Расширение: группы Zigbee «Комната · <область>» по областям Home Assistant |
| `external_extensions/bms-lib/group-membership.mjs` | Общая очередь операций по IEEE и проверенное физическое членство групп |
| `external_converters/bms-models.mjs` | Конвертер: описания моделей из `bms-models.yaml` в папке данных Z2M |
| `bms-models.example.yaml` | Образец файла с тремя закомментированными моделями (штора, реле на 2 канала, датчик) и справкой по полям |
| `test/*.test.mjs`, `test/stand.mjs` | Проверки (`node:test`): на подставных устройствах и на настоящих классах Z2M |
| `tools/stand.sh` | Стенд для проверок: настоящий Z2M версии из `versions.json` в `tuya/.work/` |

## Как Z2M их грузит

Проверено по исходникам Z2M 2.14.2 и прогоном (см. «Что проверено»):

- Z2M читает только верхний уровень `<данные>/external_converters/` и `<данные>/external_extensions/`, файлы `.js/.cjs/.mjs`
  (`lib/extension/externalJS.ts:104-112`), копирует файл во временный `.tmp-…` рядом и берёт `default`-экспорт (`:232-246`).
  Поэтому на верхнем уровне здесь только `bms-*.mjs`; дополнение копирует их как есть (`addon/stage.sh`, entrypoint).
- `import` из `zigbee-herdsman-converters` и `js-yaml` работает через ссылку `node_modules`, которую Z2M сам кладёт в эти папки (`externalJS.ts:49-72`).
- Конвертер: `default` — описание или массив описаний (`externalConverters.ts:45`), Z2M добавляет их в converters (`addExternalDefinition`).
- Расширение: `default` — класс, Z2M создаёт его как `new mod(zigbee, mqtt, state, publishEntityState, eventBus,
  enableDisableExtension, restartCallback, addExtension, settings, logger)` (`externalExtensions.ts:42-54`) и вызывает `start()`.
  Подписки — через `eventBus.on…(this, …)` (`lib/eventBus.ts`, ключ — имя класса `BmsTuyaService`), снятие — `removeListeners(this)`.
- Ошибка при загрузке файла — Z2M переименует его в `.invalid` (`externalJS.ts:212-219`). Поэтому оба файла сами ошибок не бросают.

## bms-tuya-service — что делает

Кто «устройство Tuya»:

- для служебных ответов и сырых точек — то, что прислало сообщение кластера `manuSpecificTuya` (0xEF00), с любым производителем
  (так попадают и старые `_TYST11_…`): этот кластер — только у Tuya;
- для магического пакета и `bms_dp` (сообщения от устройства в этот момент нет) — производитель с префиксом `_TZ` или `_TY`
  (`_TZE200_…`, `_TZ3000_…`, `_TYZB01_…`, `_TYST11_…`).

1. **«Который час?» и «шлюз на связи?»** (`commandMcuSyncTime`, `commandMcuGatewayConnectionStatus` кластера `manuSpecificTuya`).
   Отвечаем, только если описание модели само не ответит. Сам ответ отправляет конвертер `tuyaBase` из converters — формат не переписан.
2. **«Магический пакет» Tuya** (`tuya.configureMagicPacket` — чтение `genBasic` с атрибутом `0xfffe`): после успешного интервью и
   при повторном объявлении уже опрошенного устройства (`deviceAnnounce`), если описание не шлёт его само. `deviceJoined` не слушаем:
   он приходит до интервью, производитель ещё неизвестен, а интервью всё равно следует за ним.
3. **Сырые точки** устройства без описания (неподдерживаемого, в том числе со сгенерированным Z2M описанием): каждый отчёт
   (`dataReport` / `dataResponse` / `activeStatusReport(Alt)`) публикуется в его состояние как
   `"dp_<номер>": {"type": "bool|value|enum|bitmap|string|raw", "value": …}` (raw — строка hex). Разбирает конвертер converters
   `tuya.fz.datapoints`, он же отбрасывает повтор того же кадра.
4. **Команда `bms_dp`** такому устройству: MQTT `zigbee2mqtt/<имя>/set` с `{"bms_dp": {"dp": N, "type": "…", "value": …}}` →
   `dataRequest` хелперами `tuya.sendDataPoint*`. Типы: `bool` (true/false), `value` (целое, 4 байта), `enum` (0…255),
   `bitmap` (0…255 — так кодирует converters), `string`, `raw` (строка hex). Ошибка в команде — строка в журнале Z2M (`bms:tuya`), ничего не отправляется.
5. **Чистка таблицы групп после интервью.** У устройств, перенесённых с хаба Tuya, в таблице групп остаются его записи, и `genGroups.add`
   от Z2M на них таймаутит (живая сеть: 2 из 18 TS0502B; помог `bridge/request/group/members/remove_all`). Поэтому после успешного интервью
   (`deviceInterview` со статусом `successful` — его даёт только интервью: zigbee-herdsman `controller.ts:896` и повторное интервью по запросу,
   Z2M `lib/model/device.ts:86`; повторное подключение опрошенного устройства интервью не запускает, `controller.ts:902`) устройству `_TZ…`/`_TY…`
   шлётся `genGroups.removeAll` на каждый endpoint с серверным `genGroups` — но только если по базе Z2M оно не входит ни в одну группу
   (`zigbee.groupsIterator` — группы базы zigbee-herdsman и их участники, `lib/zigbee.ts:400`; сравнение по адресу устройства, любой endpoint).
   Устройства, которые сами шлют вкл/выкл (клиентский `genOnOff` — пульты, кнопки сцен: их группы в таблице привязок), не трогаются.
   Проверка базы и очистка **всех endpoint одного IEEE** выполняются под одной блокировкой. Штатные изменения групп
   в BMS-патче Z2M используют эту же блокировку: добавление второго канала не вклинивается между двумя `removeAll`.
   После каждой очистки `getMembership` должен вернуть пустую таблицу; успех отправки не считается подтверждением очистки.
   Один раз за интервью, без повторов; ошибка (спящее устройство) — строка
   `BMS: …` уровня warning, остальные endpoint всё равно чистятся. Удача — строка `BMS: очищена таблица групп на '<имя>' (endpoint …)`.

### Как определяется «описание отвечает само»

- **Время и статус** — статическим реестром возможностей. Конвертеры на пробном устройстве больше **не запускаются**.
  `ignore_tuya_set_time` распознаётся по идентичности, `tuyaBase` закреплённой версии — по форме его функции;
  default `timeStart` читается из опубликованного описания опции `time_start` (другого публичного метаданного upstream не даёт).
  Время при default `off` обслуживает BMS, при `1970`/`2000` — описание; статус всегда остаётся `tuyaBase`, включая `forceTimeUpdates`.
  Если формат upstream изменится, консервативно сохраняем владение ответом у описания; контракт покрыт тестами реальных моделей.
  Незнакомый пользовательский обработчик также сохраняет владение. Явное переопределение для внешнего описания:
  `meta: {bmsTuyaServices: {commandMcuSyncTime: "fallback", commandMcuGatewayConnectionStatus: "definition"}}`.
  Отсутствие обработчика означает fallback BMS. Опция устройства `time_start: "off"` отключает наш ответ на время.
- **Отсчёт времени** — 1970, или `time_start` устройства, если там `"1970"`/`"2000"`. Почему 1970: из 689 вызовов `tuyaBase`
  в converters 26.115.1 отсчёт задан у 106 — `"1970"` у 76, `"2000"` у 30; в описании опции `"1970"` назван рекомендуемым.
- **Магический пакет** — по исходному описанию converters (`findDefinition`, до слияния `configure` в одну функцию): ищем
  `tuya.configureMagicPacket` среди `configure` описания и его modern-extend (`tuyaBase`, `tuyaMagicPacket`), а у собственных функций
  `configure` — упоминание `configureMagicPacket` в тексте функции. Из 788 описаний converters с отпечатком `_TZ…` пакет шлют сами 672.
  Если описание вызывает пакет через свою вспомогательную функцию, мы этого не увидим и пошлём ещё одно чтение — безвредно (одно лишнее чтение атрибутов).

### Ограничения (через API внешних расширений не обойти — хаками не обходил)

- **Строка в журнале на `bms_dp`.** Встроенный обработчик Z2M (`lib/extension/publish.ts`) тоже получает `…/set` и, не найдя у описания ключа
  `bms_dp`, пишет ошибку `No converter available for 'bms_dp' on '<имя>'`. Команда при этом уходит (её отправляет наше расширение).
  Убрать строку можно только подменой описания устройства изнутри Z2M — не делаю.
- `dp_<номер>` видно в состоянии устройства (MQTT и вкладка «Состояние»), но не в «Exposes» и не в Home Assistant: у неописанного
  устройства нет описания, из которого Z2M строит сущности. Для сущностей — завести модель в `bms-models.yaml`.
- `bms_dp` и `dp_<номер>` — только для устройств без описания; у описанных — их собственные свойства.
- Команда всегда `dataRequest`; `sendData` (нужен 9 описаниям converters) не поддержан.

## bms-area-groups — группы по комнатам

Одна групповая команда на комнату вместо команды каждой лампе (как у хаба Tuya). Расширение читает из Home Assistant
реестры областей, устройств и сущностей (WebSocket API через Supervisor: `ws://supervisor/core/websocket`, токен
`SUPERVISOR_TOKEN`; в `config.yaml` дополнения — `homeassistant_api: true`). Устройство Z2M ↔ устройство HA — по
идентификатору discovery `["mqtt", "zigbee2mqtt_<ieee>"]`; область — у сущности `light`/`switch` (unique_id
`<ieee>_light|switch[_<endpoint>]_<base_topic>`), а если у неё своей нет — у устройства; так каналы реле могут жить в разных
комнатах. Для области, где не меньше двух устройств с серверным `genGroups`, держится группа `Комната · <область>` с id
1000–1999, закреплённым за областью в `<данные>/bms-area-groups.json`; состав приводится к области, область удалили (или в
ней осталось одно устройство) — группа удаляется, переименовали — группа переименовывается. Чужие группы (вне диапазона
или без приставки, например «Все лампы» id 1) не трогаются никогда; имя, занятое чужой группой, — предупреждение, не правка.
Всё делается запросами bridge через шину Z2M (`group/add|rename|remove`, `group/members/add|remove` с `transaction`), то есть
тем же кодом, что из интерфейса: configuration.yaml, база, `bridge/groups` и discovery светильника группы в HA — штатно.
Проход — через 30 с после старта Z2M и через 10 с тишины после событий `area/device/entity_registry_updated`; команды в
эфир по одной с паузой 1,5 с; таймаут — строка в журнале и повтор (2 мин, растёт до 30 мин). Нет `SUPERVISOR_TOKEN` —
одна строка `info` и выключение; HA не принял токен — одна строка `warning` и выключение; HA перезапустился — переподключение.
Ограничения: устройство, которое не отвечает, держит удаление своей группы до ответа (группа удаляется только пустой —
иначе `group/remove` снял бы участников подряд без пауз); группа появляется, только когда у ламп есть сущности в HA
(discovery Z2M); на железе не проверено (проверки — `area-groups.test.mjs` и `area-groups.z2m.test.mjs`).

### Надёжность синхронизации и членства

- Подключение WebSocket и авторизация ограничены 15 с каждое, запрос HA — 20 с. Ошибка отправки,
  молчащий запрос и ошибка любой из трёх подписок закрывают текущий сеанс, отклоняют все его ожидания
  и запускают переподключение с ограниченным экспоненциальным интервалом. Новый сеанс подписывается на все три события.
  Запоздалые сообщения старого сокета игнорируются. Неверный токен остаётся явной ошибкой, без бесконечных повторов.
- На каждом проходе существующее членство проверяется командой `genGroups.getMembership` непосредственно на устройстве.
  Если база содержит участника, а устройство потеряло группу, отправляется повторный `add`, затем проверяется результат.
  Таймаут/некорректный ответ оставляет членство неподтверждённым; в BMS-патче Z2M такую группу нельзя использовать
  для автоматической замены индивидуальных команд групповой.
- Реестр `zigbee[Symbol.for("bms.groupMembership")]` общий для обеих копий внешних расширений и штатных BMS-патчей Z2M.
  В `bms-lib` нет глобального singleton: временное переименование файла загрузчиком не создаёт независимых очередей.
  `withDeviceLock(ieee, callback)` охватывает всю операцию на устройстве; `invalidate(ieee, endpoint?)` сбрасывает доказательство;
  `verify(endpoint)` проверяет устройство, `isVerified(group)` требует подтверждения **всех** участников.
  Запрос bridge не ожидается внутри этой блокировки, иначе штатный обработчик заблокировал бы сам себя.
- После interview/announce доказательства сбрасываются и планируется новый проход комнат. Ответ проверки,
  начатой до переподключения, не может заново подтвердить старое членство. После перезапуска подтверждений нет;
  они получаются заново. Ручные группы, не относящиеся к HA, получают подтверждение при изменении членства через BMS Z2M.
- Сам запрос членства имеет таймаут herdsman 10 с. Блокировка не освобождается внешним `Promise.race`, пока
  сама Zigbee-команда ещё может выполняться. Устройства, не поддерживающие корректный `getMembership`, остаются
  без автоматической групповой оптимизации; их индивидуальные команды по-прежнему возможны.

## bms-models — как интегратору завести новую модель

1. Подключить устройство. Пока описания нет, в его состоянии в Z2M появятся `dp_<номер>` с типом и значением.
2. Нажимать кнопки на устройстве (или в его родном приложении) и смотреть, какая точка что меняет. Проверить команду до описания:
   в Z2M «Dev console» (или любым MQTT-клиентом) отправить в `zigbee2mqtt/<имя>/set`
   `{"bms_dp": {"dp": 1, "type": "bool", "value": true}}`.
3. Вписать модель в `bms-models.yaml` **в папке данных Z2M** (у дополнения — `/config/bms_zigbee/bms-models.yaml`, рядом с `configuration.yaml`).
   Образец и справка по полям — `bms-models.example.yaml`: `fingerprint` (modelID + manufacturerName из «О устройстве»), `points` — точки.
4. Перезапустить дополнение. В журнале должно быть `bms:models: bms-models.yaml: модель <имя>, точек: N` и `Loaded external converter 'bms-models.mjs'`.
   Ошибка в модели — строка `bms:models` с номером модели и причиной; эта модель пропускается, остальные работают.

Виды точек и чем они собраны (всё — кирпичи converters 26.115.1):

| `kind` | Свойство Z2M | Из converters |
|---|---|---|
| `switch` | `state` (ON/OFF), с `endpoint: l1` — `state_l1` | `tuya.modernExtend.dpOnOff` |
| `binary` | `<name>` (true/false) | `dpBinary` |
| `numeric` | `<name>`, `scale` — делитель | `dpNumeric` |
| `enum` | `<name>`, `values {подпись: число}` | `dpEnumLookup` |
| `cover_control` | `state` (OPEN/STOP/CLOSE) | `dpEnumLookup`, общий значок шторы `cover_position()` |
| `cover_position` | `position` 0 (закрыта)…100 (открыта) | `tuya.getHandlersForDP` (готового modern-extend для штор в 26.115.1 нет) |

- Каждому описанию добавляется `tuyaBase({timeStart: "1970"})` — как у описаний converters: магический пакет, версия MCU, ответы на время
  и статус. Описание работает и без расширения; расширение видит, что описание отвечает само, и молчит.
- Штора «наоборот» и мотор, не доходящий до края (особенность `cover_position_inverted` из `library/categories.json`: закрытая 100, открытая 7):
  `invert: true` или оба края `closed_raw` / `open_raw`. Значения за краем прижимаются к 0…100.
- Каналы многоканального реле TS0601 (`endpoint: l1`, `l2`…) — все на конечной точке 1, как в converters (`meta.multiEndpoint`).
- Файла нет — конвертер ничего не регистрирует (строка `info` в журнале). Файл не читается или не список — ничего не регистрирует, строка `error`.
  Лишнее поле в точке (опечатка вроде `scal`) — ошибка модели, а не молчаливый пропуск.
- Описание из YAML перекрывает встроенное описание converters с тем же отпечатком (Z2M ставит внешние кандидаты первыми — `findDefinition`; проверено в `z2m.test.mjs`).

## Как проверить

Нужен Node 22 и доступ к npm (один раз, для стенда).

```bash
cd ~/bms-zigbee/tuya
layer/tools/stand.sh                      # Z2M 2.14.2 в .work/z2m-app (раскладка как /app в образе дополнения)
node --test layer/test/*.test.mjs         # 58 проверок; без координатора и живой сети
```

- `service.test.mjs` (21) — расширение на подставных устройствах, но с **настоящими описаниями converters** (BAB-1413_Pro — tuyaBase 2000,
  CTL-Mini-DTP-TYZ/AC — tuyaBase по умолчанию, NAS-AB02B0 — tuyaBase + ignore_tuya_set_time, WHD02 — пакет в своей функции configure,
  SMART-HEAT10 — без пакета). Перед расширением сообщение проходит через конвертеры описания, как в Receive Z2M, и считается, сколько ответов
  ушло всего: ровно один. Отдельно: `_TYST11_` (EF00 без `_TZ`) — всё работает; EF00 от производителя без `_TZ`/`_TY` — служебные ответы есть,
  магического пакета и `bms_dp` нет; обычное не-Tuya устройство — ничего не отправлено и не опубликовано. Таблица групп: новое устройство Tuya
  без групп — `removeAll` на endpoint 1 и 2, не на 242 без `genGroups`; уже в группе — ничего; не-Tuya, без серверного `genGroups`, пульт — ничего;
  таймаут на одном endpoint — строка в журнале, второй всё равно чистится, исключения нет.
- `models.test.mjs` (6) — сборка описаний из YAML (раскомментированный пример обязан собираться), разбор отчётов и команды, калибровка шторы,
  пропуск ошибочных моделей, отсутствие и поломка файла.
- `z2m.test.mjs` (7) — **настоящие классы Z2M** из стенда: `ExternalConverters`, `ExternalExtensions`, `Receive`, `Publish`, `EventBus`, `Device`,
  папка данных как у дополнения. Z2M сам кладёт ссылку `node_modules`, грузит оба файла без ошибок, находит описание из YAML по отпечатку,
  его Receive разбирает точки описания из YAML, его Publish отправляет `position` описанию из YAML; каждому устройству — один ответ на время/статус;
