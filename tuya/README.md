# tuya — библиотека точек данных Tuya

Большинство Zigbee-устройств Tuya (модель `TS0601`) говорят «точками данных» (DP): номер + тип + значение.
Zigbee2MQTT понимает такое устройство, только если для его модели вручную описано, какая точка что значит.
У нашей интеграции BMS Integration (форк LocalTuya для Home Assistant) эти знания уже есть — как набор
пресетов «категория Tuya → точки → сущности Home Assistant». Эта папка переносит их в данные, которыми
позже воспользуется наш слой Tuya в Z2M.

## Что здесь лежит

| Путь | Что |
|---|---|
| `library/categories.json` | Сама библиотека: 91 категория Tuya, 1802 точки, у каждой записи источник `файл:строка` |
| `library/crosscheck.md` | Сверка библиотеки с zigbee-herdsman-converters 26.115.1 (11 моделей, 76 точек) и ответ на вопрос про категорию по `_TZE200_…` |
| `library/load.mjs` | Загрузчик и проверка (`loadLibrary()`, `validate()`), без зависимостей, Node 22 |
| `test/library.test.mjs` | Проверки на `node:test`, 18 штук |
| `tools/extract_bms.py` (+ `bms_load.py`, `bms_tables.py`, `bms_format.py`) | Сборка `categories.json` из репозитория BMS Integration |
| `tools/scan_converters.mjs`, `crosscheck.mjs`, `crosscheck_spec.json`, `crosscheck_prose.mjs` | Сборка `crosscheck.md` |
| `layer/` | Слой Tuya для Z2M (расширение служебных ответов и конвертер моделей из YAML) — свой README: `layer/README.md` |
| `.work/` | Временное (снимок BMS, скачанные converters); в `.gitignore`, восстанавливается командами ниже |

## Откуда данные и что важно знать

Источник — ветка `main` репозитория BMS Integration (GitHub `optomtr/bmsintegration`), коммит
записан в самом JSON (`source.commit`). Репозиторий только читается: скрипт берёт снимок через `git archive` в `.work/bms-main/`,
рабочее дерево и ветки не трогает. Пресеты — это Python-файлы `core/ha_entities/*.py`; скрипт **исполняет** их (с заглушками вместо Home Assistant)
и снимает значения у самих пресетов, а номер строки каждой сущности ловит в момент её создания. Поэтому ссылки `файл:строка` не могут быть
выдуманными; дополнительно скрипт сверяет, что на каждой из 815 строк стоит `LocalTuyaEntity(` и читаются её коды.

Три вещи, которые нельзя упустить:

1. **Пресеты хранят коды точек, а не номера.** Номер интеграция получает у облака Tuya в момент настройки (`cloud_api.py:473`, `:493`).
   Прямо назван только один номер — `paint_colour_data` = DP 61 (`light.py:54`); он стоит в `dp` у 4 точек. Остальные `dp` — `null`: «источник не называет».
   Два других номера из отчётов BMS (`colour_data` = DP 5 и DP 24) лежат отдельно, в `observed_numbers`, потому что они зависят от изделия.
2. **Значения по умолчанию — запасные.** `min`/`max`/`step`/`scale`/`precision`/`enum_*` в пресете используются, только если облако не описало точку
   (`ha_entities/__init__.py:161`). Поле `from_cloud` перечисляет, какие поля интеграция заменяет. У Zigbee-слоя облака нет — эти значения надо брать у модели.
3. **Пресеты взяты из Wi-Fi-мира Tuya.** Для Zigbee-моделей они дают набор кодов и смысл, но не полны: из 76 проверенных точек Zigbee-моделей 20 пары в библиотеке не имеют
   (подробно — `library/crosscheck.md`).

Русское название категории (`name_ru`) — перевод английской подписи из источника (`name_en`); у семи категорий подписи в источнике нет, так и записано.
Константы Home Assistant оставлены по имени (`ha:UnitOfTemperature.CELSIUS`), без подстановки «°C» по памяти.

## Как устроен `categories.json`

`categories.<код>` → `points[]` (уникальны по `code`) → `uses[]` (где и как точка использована). Подробнее — раздел `conventions` внутри файла. Кратко:

```
"percent_state": { "code": "percent_state", "dp": null, "dp_type": null, "uses": [
  { "platform": "cover", "role": "current_position_dp", "alternatives": ["percent_state","percent_control"], "priority": 1,
    "source": ".../covers.py:39", "category_source": ".../covers.py:38" } ] }
```

- `alternatives` — коды одной роли; автонастройка берёт **первый найденный** у устройства (`ha_entities/__init__.py:111-113`).
- `quirks` — особенности (штора наоборот, цвет лент в DP 61, точность температуры, форматы `colour_data`…), у каждой источники и дословная цитата.
- `value_maps` — таблицы «значение точки → состояние Home Assistant».

## Как пополнять

* **Обновить из BMS Integration** (после изменений в `main`): `python3 -I tools/extract_bms.py` и `npm test`.
  Если скрипт ругается на цитату — строка в источнике сдвинулась: поправьте номер строки в `tools/bms_tables.py`.
* **Добавить номер, особенность или перевод** — только в `tools/bms_tables.py`: запись обязана нести ссылку и дословную цитату, скрипт проверит, что цитата стоит на этой строке.
  Руками `categories.json` не править: следующая сборка сотрёт правку (а `extract_bms.py --check` покажет расхождение).
* **Добавить номера по моделям** (то, что нужно слою Tuya, раз номера определяет модель) — пока не сделано, см. «Вопросы». Основа есть: `tools/scan_converters.mjs` уже выписывает из converters
  по каждой модели список «номер → имя → конвертер» со строками.
* **Расширить сверку**: добавить модель в `tools/crosscheck_spec.json` и перегенерировать `crosscheck.md`.

## Команды

Нужны Node ≥ 22 (проверки, сверка), Python ≥ 3.12 и git (сборка из BMS Integration), `curl` для скачивания converters.

```bash
cd ~/bms-zigbee/tuya
npm test                                   # проверки библиотеки (Node 22, без зависимостей)
export BMS_INTEGRATION_REPO=<путь к локальной копии optomtr/bmsintegration>   # по умолчанию ~/bmsintegration
python3 -I tools/extract_bms.py            # пересобрать categories.json из main BMS Integration
python3 -I tools/extract_bms.py --check    # убедиться, что файл равен свежей сборке

# сверка с converters (версия — из ../versions.json)
mkdir -p .work/converters-src && cd .work/converters-src
curl -sSL -o v26.115.1.tar.gz https://github.com/Koenkk/zigbee-herdsman-converters/archive/refs/tags/v26.115.1.tar.gz && tar -xzf v26.115.1.tar.gz && cd ../..
node tools/scan_converters.mjs .work/converters-src/zigbee-herdsman-converters-26.115.1 > .work/scan.json
node tools/crosscheck.mjs --src .work/converters-src/zigbee-herdsman-converters-26.115.1 --scan .work/scan.json --bms .work/bms-main --out library/crosscheck.md
```

## Что проверено

Подтверждено запуском (вывод — в отчёте задачи):

* `categories.json` собирается детерминированно: повторная сборка и `--check` дают тот же файл; категорий 91, точек 1802, использований 1961.
* `npm test` — 18 проверок зелёные: JSON читается; у **каждой** записи (категория, сущность, использование, номер, особенность, таблица значений) есть корректный источник;
  коды и номера точек в категории не повторяются; ссылки использований указывают на существующие сущности.
* Проверки умеют краснеть: файл нарочно ломался двумя способами (убран источник; одному номеру 61 дали две точки) — 4 из 18 красные; после возврата файл побайтно равен исходному, 18 из 18 зелёные.
  Те же поломки воспроизведены в памяти отдельными тестами `validate() замечает …`.
* Все номера строк в `crosscheck.md` и цитаты в ручных таблицах сверены скриптами с исходниками (BMS `main` и converters `v26.115.1`).

## Что не проверено

* **Ничего на железе и на стенде.** Z2M, адаптер, настоящие устройства не запускались.
* **Главное предположение не подтверждено и не опровергнуто** — «номера точек у Zigbee-устройств те же, что в облаке Tuya и BMS Integration»: сравнивать нечем (нет облачных дампов реальных Zigbee-устройств, у библиотеки почти нет номеров).
  Установлено другое: в converters номера определяются моделью, а не категорией (`crosscheck.md`, раздел «Номера по всем моделям»).
* **Категория по `_TZE200_xxxxxxxx`**: связь восьми знаков с `product_id` Tuya в BMS Integration и в converters не найдена; есть только косвенные признаки. Нужна проверка на живых устройствах (описана в `crosscheck.md`).
* Соответствие «свойство Z2M ↔ код библиотеки» в сверке сделано человеком; сверено 11 моделей из 324 с `tuyaDatapoints`.
* Не перенесены в таблицы большие бинарные справочники света (списки сцен `SCENE_LIST_*` в `light.py`); форматы `colour_data` описаны в `quirks` словами.
* Сенсоры/числа с `match_contains_any` (применимы только если в строке точки есть подстрока) перенесены как есть, их срабатывание не моделировалось.
