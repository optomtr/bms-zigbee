# Интерфейс из desktop/iPhone макетов

Дополнение `2.14.2-bms.11`, поверх `bms.10`. Визуальная основа — переданные пользователем `zigbee2mqtt-bms-desktop.html` и `zigbee2mqtt-bms-iphone.html`. Прежнее оформление заменено. Дополнительные экраны используют те же системные цвета, размеры, сгруппированные списки, карточки, сегменты и формы.

Ресурсы: [Apple Design Resources](https://developer.apple.com/design/resources/). Шрифты берутся из системного стека Apple; Inter, Google Fonts, сторонние UI-библиотеки и внешние CDN не подключаются. Скачанные шрифты или SF Symbols не встраиваются в веб-дистрибутив. SVG — обычные векторные элементы интерфейса, как в переданных HTML.

## Что работает

- Компьютер: список хабов слева, выбранный экземпляр справа, карточки устройств и разделы хаба. Телефон: список хабов, отдельный экран выбранного хаба, возврат и нижняя навигация. Светлая и тёмная темы переключаются на экране хабов.
- Устройства: поиск/фильтры, последнее состояние, LQI, показания, параметры по writable exposes, переименование. Каналы многоканальных устройств сохраняются. Ползунок отправляет значение после change.
- Комнаты из Home Assistant; ручные группы с созданием, переименованием, добавлением/удалением endpoint и удалением с подтверждением. Состав HA-комнат управляется в HA.
- Сопряжение через существующий permit_join. Перезапуск — после подтверждения и с ожиданием API-ответа.
- MQTT: безопасное отображение адреса брокера, топика, канала и версии. Брокер не объявляется проверенным по вымышленному ping.
- Карта: ручной `bridge/request/networkmap`, `type: raw`, `routes: false`, ожидание до 120 секунд. Точки располагаются условно; линии только из полученных links, без догадок по LQI/близости. Указаны время снимка, возможная неполнота; до 200 узлов. Вход на экран не создаёт радиоопрос.
- Журнал: до 50 последних предупреждений/ошибок этой вкладки. Диагностика: версии, загрузка расширений, NCP, API-события, результат `bms/self_check`, скачивание сводки без полного конфига.
- Формы: ошибки в диалоге, API transaction, отсутствие автоматических повторов, блокировка offline даже во время ввода поиска. Native dialog, Escape, возврат фокуса, reduced motion, safe area.
- `?demo=1`: отдельные явно демонстрационные устройства и топология, ни одного WebSocket. Настройка групп в demo не имитирует успешное сохранение на сервере.

## Границы макета и настоящего API

Один запущенный Z2M обслуживает один координатор. В исходных HTML несколько хабов, их включение/удаление и создание имитировались таймерами; этот код не переносится как рабочий backend. В UI отображается текущий экземпляр. «Другой хаб» открывает HTTP(S)-адрес отдельно настроенного экземпляра, без передачи токена текущей вкладки. Для нескольких координаторов устанавливаются отдельные экземпляры с разными топиками.

Сложные функции Z2M (OTA, bindings, составной цвет, аппаратные настройки) доступны в «Расширенных настройках» (`?advanced=1`). Карта не доказывает маршруты каждой команды, MQTT-state не доказывает физическое исполнение. Самопроверка относится ко времени её выполнения и не включает спящие батарейные устройства.

## Проверка и запуск

Исходники: `addon/bms_zigbee/rootfs/opt/bms-ui/`. Сохраняется штатный HTTP/WebSocket Z2M, ingress-prefix, авторизация и исходный расширенный UI. UI-файлы входят в паспорт образа.

```bash
node --test addon/test/*.test.cjs
NODE_PATH=/path/to/playwright/node_modules node addon/test/frontend-browser.cjs
BMS_UI_BROWSER=webkit NODE_PATH=/path/to/playwright/node_modules node addon/test/frontend-browser.cjs
```

Браузерный стенд подменяет WebSocket и не управляет оборудованием. Проверяются команды, отсутствие optimistic-подтверждения, ползунок, группы, ошибки, авторизация, XSS, offline, карта по явному запросу, demo и мобильные экраны/темы. GitHub Actions повторяет Chromium и WebKit, тесты ядра/Z2M/слоя/harness, stage и Docker build. Настоящий Supervisor ingress и физическое оборудование требуют приёмки на установленном дополнении.
