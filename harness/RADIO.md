# Пассивная диагностика радио и транспорта

Это третий пакет: инструмент сбора данных для проверки гипотез. Без журналов живых сбоев нельзя утверждать, что причина в CCA, мощности или прошивке. Инструмент не меняет Zigbee-сеть, не публикует MQTT-команды, не подключается к порту 6638, не вызывает probe, reset, scan и не очищает счётчики.

## Сбор

Нужны Python 3.12+ и зависимости `harness/requirements.txt`. Запускать из `harness/` с доступом к существующему MQTT-брокеру. HA-токен и парное Tuya-устройство не нужны.

```bash
python -m zamer.radio capture --host 192.168.1.10 \
  --base-topic zigbee2mqtt --username observer --password-env BMS_MQTT_PASSWORD \
  --seconds 3900 --out capture.jsonl
```

Пароль берётся из заранее заданной переменной окружения; в аргументы и журнал он не записывается. У наблюдателя достаточно прав на чтение пяти топиков: `bridge/info`, `bridge/logging`, `bridge/bms/extensions`, `bridge/bms/tx_event`, `bridge/bms/device_report` относительно base topic. Произвольные MQTT-топики, содержимое DP, сетевой ключ и полный конфиг не сохраняются. Соединение здесь обычное MQTT TCP в локальной сети; TLS в этом инструменте пока не предусмотрен.

Журнал создаётся новым файлом, записывается построчно и ограничен 64 MiB; существующий файл не перезаписывается. Разрывы соединения, номера записей, аварийное окончание и досрочная остановка видны анализатору. Ctrl+C завершает захват с пометкой неполной длительности. Отказ подписки — ошибка, а не успешный пустой захват. Timestamp `received_at` — время получения на компьютере наблюдателя в UTC, не время радиокадра.

**Счётчики NCP/ASH штатное ядро снимает раз в час** (`WATCHDOG_COUNTERS_FEED_INTERVAL=3600000`). Значения уже являются интервалами, потому что после чтения обнуляются. Анализатор суммирует записанные выборки, не вычитает соседние. Первая выборка может включать время до начала захвата. Период по умолчанию 65 минут повышает шанс получить хотя бы один набор, но не гарантирует его при рестартах/разрывах. Для сопоставления сбоя со счётчиками записать точное время сбоя и захватить окна до и после; точной посекундной локализации эти счётчики не дают.

Нужен журнал уровня info для `zh:ember`. Если настройки скрывают эти строки, анализатор покажет отсутствие данных. События `tx_event/device_report` доступны при уже включённом `advanced.bms_device_reports: true`; сборщик сам не включает настройку и не перезапускает дополнение. MQTT-логирование Z2M подавляет одинаковые соседние сообщения; QoS 0, ротация и переподключение тоже могут терять данные. Для важных опытов сохранять и штатный файловый журнал.

## Анализ без подключения к сети

```bash
python -m zamer.radio analyze capture.jsonl \
  --herdsman 10.10.0-bms.3 --out radio-result
# Также можно передать обычный log.txt Z2M или JSON console log вместо capture.jsonl.
```

Указать реальную версию установленного ядра из журнала запуска/паспорта. Поддержаны `10.10.0-bms.3` и исходный `10.10.0`, порядок полей сверен с упакованным ядром тестом. Другая версия требует проверки контракта; несовпадение версии из журнала с аргументом останавливает анализ. Название или номер версии дополнения вместо herdsman не подходят.

Появятся `radio.json` с полными именованными счётчиками, событиями и качеством данных и `radio.md` с направлениями проверки. Папка должна быть новой. Нет счётчиков → `insufficient_data`; счётчики без выбранных признаков → `no_indicators_in_samples`, а не «радио исправно». Переполнение 16-битного NCP-счётчика отмечается как нижняя оценка. Повторно записанные записи захвата и события с теми же source session/sequence не увеличивают сумму.

| Признак | Что проверять дальше | Чего он не доказывает |
|---|---|---|
| PHY_CCA_FAIL_COUNT | Загруженность эфира и совпадение со сбоем; затем контракт прошивки | Что надо отключить CCA или послать Tuya customFrame |
| MAC/APS retries, failed | Доставку и маршруты на том же сценарии | Исполнение команды конкретным реле |
| Ошибки ASH, CRC, ACK timeout | Транспорт host↔NCP, отдельно Ethernet и UART | Что проблема именно в Zigbee или именно в кабеле |
| Buffer/queue/broadcast table overflow | Предложенную нагрузку и очереди | Что повышение мощности исправит переполнение |
| Frame counter/decryption failures | Безопасность, rejoin, историю устройства | Слабый радиосигнал |
| Успешный setPower / failed setPower | Принял ли NCP изменение; восстановилась ли базовая мощность | Фактическую мощность на антенне |

MAC, APS, ASH и MQTT — разные единицы. Процент потерянных команд из этих сумм не вычисляется. Количество `device_report` не равно количеству исполненных команд. Для доставки используются сценарии существующего замерщика с корреляцией и физическая проверка контрольных устройств.

## Порядок аппаратного эксперимента для программиста

1. Записать сборку, SHA паспорта, модель/прошивку SLZB и NCP, канал, положение устройств и маршрутизаторов, время сбоя. Проверить `bridge/bms/extensions`: ready означает успешный start, а не здоровье радиосети.
2. Повторить исходный сценарий без изменения настроек. Сохранять заданный поток команд независимо от задержек ответов; его SHA/список и фактически отправленное количество приложить к результатам. Старый последовательный load сам по себе не обеспечивает одинаковую предложенную нагрузку.
3. Снять наблюдения до/после сбоя и физическое состояние хотя бы контрольного реле. Отделить очередь приложения, отправку, device report и исполнение.
4. Выбрать **одну** переменную по данным: coalescing/throttle, concurrent 1/2/4/8/16, APS RETRY, фиксированная мощность/boost или совместимая версия NCP. Использовать изолированный стенд и чередующиеся повторения A/B/A, без одновременной смены канала и прошивки. Сравнивать задержки p50/p95/p99, исполнение, нарушения порядка, восстановление и счётчики каждого слоя.
5. CCA — только при соответствующих признаках и проверенном контракте конкретной прошивки. Байты из Tuya-прошивки не переносить вслепую. Прошивки проверять на отдельном координаторе.
6. До опыта заполнить критерии в `examples/radio-experiment.json`; после — журналы и решение go/no-go. Пустые пороги означают «критерии не заданы», не успех. Этот файл — протокол для человека, не автоматический разрешатель изменения радио.

## Проверено

Тесты проверяют контракт с vendor, read-and-clear, разделение слоёв, неверную версию/длину/значения, насыщение, retained, разрывы, повторы/пропуски, фильтрацию секретов, файловый CLI и отсутствие publish у MQTT-сборщика. Проверки используют искусственные данные; физические гипотезы и реальная сеть ещё не проверены.
