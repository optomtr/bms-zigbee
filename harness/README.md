# Замерщик стенда BMS Zigbee

## Что это

Программа, которая доказывает (или опровергает) «наш Zigbee не хуже хаба Tuya».
На стенде два одинаковых набора устройств: один на родном хабе Tuya (в Home
Assistant через BMS Integration), второй — у нас: Zigbee2MQTT на координаторе
SLZB-06M. Замерщик гоняет одни и те же сценарии на обеих сторонах одновременно,
пишет всё в одну базу SQLite и выдаёт одну таблицу: обе стороны рядом по шести
замерам.

Главное правило: **засчитываем только ответ самого устройства**, а не то, что
показывает интерфейс. Как это сделано на каждой стороне — ниже, со ссылками
на исходники.

## Как поставить

```sh
cd ~/bms-zigbee/harness
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt     # paho-mqtt, aiohttp, PyYAML, pytest
cp example.config.yaml config.yaml            # и вписать свои адреса и устройства
export HA_TOKEN=...        # долгоживущий токен АДМИНИСТРАТОРА Home Assistant
export MQTT_PASSWORD=...   # если у брокера есть пароль
```

Что должно быть настроено вне замерщика:

- **BMS Zigbee bms.7+**: включить `advanced.bms_device_reports: true` и
  перезапустить дополнение. Стенд требует `bridge/bms/capabilities` schema 1.
  `optimistic: false` больше не используется как доказательство происхождения.
  Для стандартного on/off сопоставляется сырой `genOnOff.onOff`; для EF00
  задать `ours.report_dp` и `ours.report_values`, для других кластеров —
  `ours.report_cluster`, `ours.report_field`, `ours.report_values`.
  Для подтверждения требуется коррелированная отметка приёма команды самим Z2M.
- **HA**: токен администратора — подписка на события `bms_integration_*`
  обычному пользователю не разрешена.
- Компьютер с замерщиком, брокер MQTT и HA не должны сидеть на «фильтре»,
  который выключают в сценарии 2.

## Как запустить

```sh
.venv/bin/python -m zamer scenarios              # список сценариев
.venv/bin/python -m zamer check                  # подключиться к обеим сторонам и проверить настройки
.venv/bin/python -m zamer run 1                  # сценарий 1 (сутки)
.venv/bin/python -m zamer run 4 --duration 30m   # сценарий 4 на 30 минут
.venv/bin/python -m zamer run 2 --outage 5m --limit 30m --probe 15s
.venv/bin/python -m zamer report                 # report.md + report.csv рядом с базой
```

Ключи `run`: `--duration` (1, 3, 4, 7), `--outage` (2), `--limit` (2, 5, 6),
`--probe` (2, 6, 7), `--lost-after` (7), `--devices a,b` — только эти пары.
Длительности: `90s`, `30m`, `24h`, `7d`. Конфиг по умолчанию — `config.yaml`
в текущей папке, другой — `-c путь`. Ctrl+C прерывает прогон, сделанное
остаётся в базе с пометкой «прервано».

| № | Сценарий | Что делает оператор | Что пишется |
|---|---|---|---|
| 1 | обычная работа, сутки | ничего | команда каждому исполнительному раз в 10 с, отчёты датчиков |
| 2 | отключение света | выключить фильтр, через 5 мин включить (Enter) | через сколько каждое устройство ответило |
| 3 | убрали повторитель | выдернуть повторитель (Enter) | команды дальним (`far: true`): доля доставки и первая доставка |
| 4 | шум Wi-Fi | описать условия | как 1, коротко (30 мин), условия в `runs.conditions` |
| 5 | подключили рядом, унесли | отнести датчики (Enter) | первый отчёт каждого датчика после переноса |
| 6 | перезапуск | перезапустить координатор/Z2M и хаб (Enter) | через сколько каждое устройство ответило |
| 7 | неделя без вмешательства | ничего | проба раз в 30 мин; «потеряно» — молчит дольше 2 ч |
| 8 | новая модель | ответить «видны ли данные» по каждой стороне | наблюдение оператора |

Перед сценариями 1, 3, 4, 7 идёт «прогрев» — по одной команде каждому
исполнительному без записи: замерщик всегда командует противоположное тому,
что устройство сообщило последним, и ему нужно это узнать.
«Вернулось» в сценариях 2 и 6: исполнительное — подтвердило команду (пробуем
раз в `--probe`), датчик — прислал отчёт. Признак «в сети» не используем: Z2M
и интеграция считают его по-разному, а ответ на команду — одинаково.

## Как отличаем подтверждение устройства

### Наша сторона (BMS bms.7, device_report schema 1)

Патч Z2M `0005-device-report-provenance` публикует прямой результат конвертации
входящего кадра в `bridge/bms/device_report` **до** cache_state, debounce,
throttle и groupOptimistic. Сообщение не retained; содержит session_id,
sequence, received_at, IEEE, endpoint, cluster, type, raw и payload. Отложенные
callback-публикации конвертера не считаются свежими отчётами.

Обычные MQTT state, retained и groupOptimistic никогда не подтверждают команду.
Кроме нужного поля в payload требуется соответствующий сырой атрибут/DP в том
же кадре. Это защищает и от конвертера, который вернул state из meta.state:
посторонний отчёт мощности не станет подтверждением реле.

- Стандартный switch: `genOnOff`, attributeReport/readResponse, сырой onOff 0/1.
- Tuya EF00: явно задать `ours: {friendly_name: relay, endpoint: 1, report_dp: 7,
  report_values: [1, 0]}`. Номер DP выясняется для fingerprint; пример 7 не универсален.
- Другой кластер: `ours.report_cluster`, `ours.report_field` — ключ raw верхнего
  уровня, `ours.report_values: [сырой_вкл, сырой_выкл]`. Без соответствия — timeout.
- Многоканальное реле: отдельная пара на канал, один friendly_name,
  `ours.endpoint: 2`, `ours_key: state_l2`; ожидания хранятся по имени пары.

Стенд передаёт служебный `__bms_command_id` вместе с set. Publish удаляет его
до конвертеров/склейки и пишет `mqtt_intent` с command_id и received_at.
Подтверждение допускается только после коррелированной отметки намерения:
`device_report.received_at > mqtt_intent.received_at`, оба времени сняты тем же
процессом Z2M. Равная миллисекунда неоднозначна и отвергается. Старые sequence
и другая session также отвергаются. Отметки не зависят от часов машины стенда.
`CommandResult.detail` содержит command_id и session/sequence/cluster/endpoint.

Это доказательство свежего отчёта о значении, **не** физического переключения
нагрузки и не криптографическая связь с конкретной командой: протокол устройства
может не возвращать идентификатор нашей команды. Для пилота чередовать значения
и сверять часть исполнений физически. Модели, которые отвечают только через
отложенный callback, пока не поддерживают достоверный замер этим методом.

Отдельные счётчики сохраняются в observations каждого прогона и выводятся
`run_summary`: команды стенда MQTT, обычные state (игнорированы), входящие
конвертированные отчёты, подтверждения, invalid/stale/unverified, а также
`mqtt_intent`, `group_frame`, `unicast_frame` из `bridge/bms/tx_event`.
Последние — попытки вызовов API ZCL, не число радиоповторов. Реальный эфир
измеряется отдельно сниффером/NCP. `bridge/logging` ускоряет обнаружение отказа;
отсутствие отчёта приводит к timeout.

### Сторона Tuya (BMS Integration, ветка main, 60af1e1)

**Ловушка подтверждена кодом:**

- `entity.py:546` → `coordinator.py:1010-1034` (`apply_optimistic_status`) —
  ожидаемое значение сразу пишется и в `self._status`, и в кэш протокола
  (`dps_cache`), и рассылается сущностям: HA показывает новое состояние до
  любого ответа. Откат — `coordinator.py:1037-1058` (`restore_optimistic_status`),
  вызывается из `entity.py:527` при отказе/обрыве; при таймауте шлюза
  (`entity.py:514-522`) — не откатывается, а через 6 с опрашивает хаб
  (`coordinator.py:110, 938-955`), и хаб отвечает кэшем, где уже лежит наша запись.
- Событие `bms_integration_status_update` (`coordinator.py:1529-1540`)
  сравнивает `self._status` с кэшем — после оптимистичной записи там одно и то
  же, поэтому подтверждение устройства проходит **молча**. Не годится.
- Состояние сущности в HA и успех вызова службы (`entity.py:546-550` —
  возвращается сразу; без оптимизма — по «принято» от шлюза, `entity.py:534-535`,
  а это ещё не «устройство выполнило», `entity.py:590-591`)
  тоже не годятся.

**Режим `dp_event` (работает на текущей main).** Событие
`bms_integration_device_dp_triggered` (`coordinator.py:1525-1528`) стреляет из
`status_updated`, то есть по посылке, пришедшей с сокета; оптимистичный путь
его не вызывает. Подтверждение = это событие с `device_id`, нужной `dp` и новым
значением. Ограничения, и как замерщик с ними живёт:

1. Стреляет только когда в посылке ровно одна точка данных. Посылки из
   нескольких точек (реле + таймер, датчик температура + влажность) не видны:
   такая команда уйдёт в таймаут. Поэтому в `dp_event` доставка и отчёты
   датчиков Tuya — **нижняя оценка**, это пишется под таблицей.
2. `dispatched_dps` ставится для любой расшифрованной посылки, включая ответ на
   опрос (`core/pytuya/__init__.py:1288-1289`), а `status_updated` вызывается и
   после опроса кэша хаба (`coordinator.py:955`, `:585` — после переподключения,
   `:1130`). Значит, событие может принести наше же значение из кэша хаба.
   Защита: ответ кэша приходит не раньше 5 + 6 = 11 с после команды
   (`pytuya/__init__.py:134` TIMEOUT_REPLY, `coordinator.py:110`), поэтому
   ожидание подтверждения — не больше 10 с (конфиг откажется от большего), а
   подтверждения в течение `suspect_window_s` (12 с) после таймаута и после
   возврата из «недоступно» помечаются `suspect` и не идут в счёт ни в ту, ни
   в другую сторону. Их число — под таблицей.
3. События интеграция шлёт, только если на них подписаны **именно по имени**
   (`coordinator.py:1514`), поэтому замерщик подписывается на каждое событие
   отдельно, а не на `*`.

Признаки отказа: показ откатился к прежнему (`restore_optimistic_status`),
сущность стала `unavailable`, вызов службы вернул ошибку; иначе — таймаут.
Время, когда HA сменил показ, пишется в `commands.optimistic_ms` — только для
справки (под таблицей видно, насколько показ опережает ответ).

**Режим `push_event` — минимальная правка интеграции** (не применена, интеграцию
не трогали): [patches/bms_integration_push_event.diff](patches/bms_integration_push_event.diff),
около 30 строк в двух файлах.

- `core/pytuya/__init__.py`, в `_status_update` перед `listener.status_updated(status)`:
  слушателю отдаются сырые `dps` посылки и время шлюза `t` (`getattr`, чтобы не
  менять `TuyaListener`/`EmptyListener`). Сюда приходят посылки `STATUS`
  (cmd 8) от шлюза; подтверждения команд (ACK) и обычные ответы на опрос сюда
  не попадают (`_dispatch`, `__init__.py:470-515`) — если только хаб не
  отвечает на опрос посылкой `STATUS`; это проверить на железе (п. 2 ниже).
- `coordinator.py`, новый метод `push_received`: событие
  `bms_integration_push` с `device_id`, `cid`, `dps`, `t` — на каждую посылку,
  без сравнения с кэшем; только если есть подписчик, как у соседних событий.

С правкой видны и многоточечные посылки, а подтверждение не путается с
кэшем. Окно сомнения в `push_event` пока тоже действует — убрать его
(`suspect_window_s: 0`) можно после проверки на железе (п. 2 ниже).

## Что считает отчёт

`python -m zamer report` берёт последний завершённый прогон каждого сценария.

| Замер | Откуда | Как |
|---|---|---|
| Доставка команд, % | сценарий 1 | подтверждено / (подтверждено + отказ + таймаут); `suspect` и «нет связи со стендом» не в счёте |
| Задержка, медиана, мс | сценарий 1 | от отправки до ответа устройства (через MQTT / WebSocket — у обеих сторон одинаковый путь) |
| Отчёты датчиков, % | сценарий 1 | ожидается длительность / интервал; пропуск — промежуток длиннее 1,75 интервала (ровно 2 — один пропуск, 3 — два), но не больше, чем отчётов реально пришло; лишние отчёты не раздувают |
| Возврат после отключения света, мин | сценарий 2 | когда вернулось последнее; если не все — «не все за N: вернулось k из n» |
| Потеряно за 7 суток | сценарий 7 | исполнительное без подтверждённой пробы последние 2 ч, датчик без отчёта max(2 ч, 3 интервала) |
| Новая модель видна без описания | сценарий 8 | ответ оператора |

Сценарии 3–6 в таблицу не входят (их замеров в шести нет): итог каждого прогона
печатается сразу в консоль и лежит в базе (`recoveries`, `commands`, `runs.conditions`).

## Что проверено

```sh
.venv/bin/python -m pytest -q
```

- Тесты на поддельных бэкендах (`tests/fakes.py` повторяет поведение Z2M и
  BMS Integration со ссылками на строки): подтверждение / отказ / таймаут на
  обеих сторонах; оптимистичный показ HA **не** подтверждение; `status_update`
  с ожидаемым значением — не подтверждение; ответ после таймаута — `suspect`;
  оптимистичный показ Z2M и кэш не подтверждают молчащее устройство;
  `check` требует отдельную телеметрию входящих сообщений и корреляцию команды;
  расчёт всех шести замеров; сценарии 1, 2, 3, 7, 8 целиком; настоящий клиент
  HA WebSocket против поддельного сервера (вход, подписки, службы, переподключение).
- Тесты краснеют, если сломать расчёт: засчитать показ HA как подтверждение
  (11 тестов красные), засчитать таймаут как доставку (2), убрать потолок у
  отчётов датчиков (4), принять сохранённое брокером состояние (1). Файлы
  возвращены, sha256 сверены.
- Сквозной прогон CLI без железа (`tools/e2e_local.py`): настоящий брокер MQTT
  (amqtt), поддельный Z2M на paho, поддельный HA на aiohttp; `check`,
  `run 1 --duration 20s`, `run 2` с Enter из stdin, `report` — коды 0, таблица
  верная (lamp 100 %, plug 0 % на обеих сторонах → 50 %).
- Правка интеграции: `git apply --check` по main 60af1e1 — чисто;
  `tools/check_push_patch.py` на копии с правкой — сырой push доходит до
  дочернего устройства (`{'1': True}`, `t`), подтверждение команды (ACK) — нет;
  без правки — ничего.

## Что НЕ проверено

- Ничего не запускалось на железе, с настоящим Z2M, хабом Tuya и HA с
  BMS Integration — их нет. Поддельные бэкенды — моё прочтение исходников.
- Значения для штор (`cover`): `OPEN/CLOSE` в Z2M и `open/close` в точке Tuya —
  типовые, не проверены; при другой модели — переопределить в конфиге.
- Сценарии 4, 5, 6 тестами целиком не прогнаны (они собраны из тех же
  кирпичей, что 1 и 2, которые прогнаны).
- Подключение к настоящему брокеру с паролем и TLS (TLS не поддержан).

## Что проверить на железе первым делом

1. `python -m zamer check` — Z2M без оптимизма, все сущности HA нашли `device_id/dp`.
2. Обесточить одно устройство за хабом Tuya и послать ему команду из HA: если
   `bms_integration_device_dp_triggered` (или `bms_integration_push` с правкой)
   всё равно придёт — хаб отвечает сам, и окно сомнения надо оставить или
   расширить; если не придёт — в `push_event` его можно обнулить.
3. Какие точки данных розетки/реле приходят в одной посылке: если всегда
   несколько — режим `dp_event` для них бесполезен, нужна правка.

## Открытые вопросы

- Применять ли правку `push_event` в BMS Integration (решает владелец
  интеграции). Без неё сторона Tuya меряется снизу.
- Побочная находка для задачи «ядро»: на ember у Tuya `dataRequest` уходит без
  повтора APS (`emberAdapter.ts:1979-1981`) и без ожидания ответа — один
  потерянный в эфире кадр = потерянная команда, о которой Z2M не узнает.
  Похоже на одну из причин «через Z2M работает плохо».
- Сценарий 7 трогает исполнительные устройства раз в 30 мин (проба); если
  «без вмешательства» означает совсем без команд — нужен другой признак жизни.
